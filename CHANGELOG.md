# Evolyon Theme — Changelog

## Unreleased — 2026-09-06

### Fixed

- **The `open_basedir restriction in effect` warning on every wp-admin page, reported directly by the user, still appeared after an earlier fix attempt.** Root cause confirmed by reading Elementor's own bundled `vendor/elementor/wp-one-package` admin code: it registers a "Theme Builder"-style submenu item whose slug is a full URL rather than a page slug, which trips a `file_exists()` call in WordPress core's `wp-admin/menu-header.php` (line ~263) when building that link. The existing compatibility fix (`Evolyon_Elementor::fix_elementor_malformed_submenu_slugs()`) was correct in what it removes, but ran on the `admin_menu` action at a fixed priority (99999) — not late enough, since Elementor registers a related admin-menu callback at `PHP_INT_MAX` priority on that same action, which runs *after* our fixed priority. Moved the fix to the `admin_head` action instead: a separate, later action core always fires after `admin_menu` has fully finished and strictly before `menu-header.php` is included, so it's guaranteed to run after every `admin_menu` callback regardless of that callback's own priority. Verified by rendering `wp-admin/menu.php` + `menu-header.php` in isolation: the malformed item is confirmed present immediately after `admin_menu` completes, confirmed removed after `admin_head` fires, and the render that follows produces zero `file_exists()`/`open_basedir` warnings.

### Removed

- **All WooCommerce integration removed from the theme**, per explicit product direction after a performance investigation found the Elementor+WooCommerce combination adding significant per-request overhead in this environment. Deleted `inc/woocommerce/` (the whole `Evolyon_WooCommerce` integration class: shop hero, content-wrapper replacement, placeholder-image fix, asset enqueueing), `assets/css/woocommerce.css`, `assets/js/woocommerce.js`, `assets/images/product-placeholder.svg`, and the header builder's Cart element (`inc/header-builder/elements/class-element-cart.php`). Removed `'cart'` from every hardcoded header default (`Evolyon_Header_Config::defaults()`, `mobile_defaults()`, the `two_row` variant, and `MOBILE_ELEMENT_TYPES`) and the corresponding CSS/JS (header.css's mini-cart dropdown block, header-frontend.js's cart-toggle handler). The Account element and its own header/dashboard integration are untouched — that's a general customer-account feature, not WooCommerce-specific. The theme has no WooCommerce coupling left; it works identically whether or not WooCommerce is installed.

### Fixed

- **WooCommerce's own gray placeholder image, used on every product without a real photo, wasn't actually replaceable through the `woocommerce_placeholder_img_src` filter alone.** That filter only feeds `wc_placeholder_img_src()`; the function that actually prints a product loop's `<img>` — `wc_placeholder_img()` — checks `wp_attachment_is_image()` on the `woocommerce_placeholder_image` *option* first, and every WooCommerce install auto-creates a real media-library attachment for its own bundled placeholder on activation, which short-circuits before the filter is ever consulted. Confirmed live: with only the filter in place, product cards still rendered WooCommerce's own placeholder.webp. Fixed in `Evolyon_WooCommerce::maybe_set_placeholder_image()` (theme's `inc/woocommerce/class-evolyon-woocommerce.php`) by replacing the option's value directly with a new on-brand SVG (`assets/images/product-placeholder.svg` — an editorial line-icon illustration on the theme's own palette, dark-mode aware) — one-time, and only when the option still points at WooCommerce's own auto-generated default, so a site owner who has since chosen their own placeholder in Settings > Products is never overwritten. The `woocommerce_placeholder_img_src` filter is kept as a defensive fallback. Verified live via computed styles: every product image across the Shop archive, a demo homepage's product grid, and the hero spotlight card now resolves to the new SVG.
- **`assets/css/woocommerce.css` wasn't enqueued on any page outside WooCommerce's own recognized page types** (`is_woocommerce()`/cart/checkout/account) — real gap surfaced while building the new eCommerce demo homepage (see plugin changelog), which embeds a real `[products]` shortcode on an ordinary page. Without this, that shortcode's product grid rendered with zero styling: no card layout, no price color, no on-sale badge. `Evolyon_WooCommerce::enqueue()` now also loads on any singular page whose content contains the `[products]` shortcode.

### Added

- **On-brand SVG product placeholder** (`assets/images/product-placeholder.svg`) replacing WooCommerce's bundled gray box — see the Fixed entry above.

## Unreleased — 2026-09-02

### Fixed

- **Real RTL bidi rendering bug found in a targeted competitive-QA pass**: on the empty Cart/Checkout state in RTL, WooCommerce Blocks' own "Your cart is currently empty!" message rendered with the punctuation pulled to the front ("!Your cart is currently empty") — a standard Unicode Bidi Algorithm behavior when an untranslated Latin-text run ending in neutral punctuation sits inside an RTL-direction ancestor. Not a translation gap this theme should fill (it's WooCommerce core's own string) and not fixable by adjusting logical alignment — fixed with `unicode-bidi: plaintext` on `.wc-block-cart__empty-cart__title`/`.wc-block-checkout-empty__title` in `assets/css/woocommerce.css`, which resolves each element's own text direction from its first strong character instead of inheriting the page's RTL direction. Verified live: punctuation now reads correctly in RTL

## Unreleased — 2026-09-01

### Fixed

- **Real, serious bug: the Elementor compatibility stylesheet (`elementor.css`) has never loaded on any page, ever.** It was hooked to `elementor/frontend/after_enqueue_style` (singular) — a hook name that doesn't exist; Elementor's real hook is `elementor/frontend/after_enqueue_styles` (plural). Confirmed by building a real Elementor test page (container + native Heading widget + native Text Editor widget + the theme's own custom Button widget) and inspecting loaded stylesheets directly: `elementor.css` was completely absent, and the native Heading widget rendered in Elementor's own default Roboto/blue instead of the theme's fonts/colors — while the custom Button widget (which doesn't route through Elementor's typography system) was correctly styled, which is what made this invisible until specifically tested. Fixed the hook name, and while fixing it also extended `elementor.css` to cover native Heading and Text Editor widgets specifically (font-family, weight, and color, all needing `!important` since Elementor's own per-post generated stylesheet uses the identical selector and loads later) — previously only `.elementor-button` had any override at all. Verified live: native widgets now correctly show the theme's display/body fonts and text color
